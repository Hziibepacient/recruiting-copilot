# 简历与面试讲解 · AI 应用开发

## 项目定位

推荐名称：**Recruiting Copilot｜基于简历证据的招聘 AI 助手**。

一句话：让 AI 读简历并给出可追溯的判断，再由本地工具可靠执行联系动作。

你最适合强调的是：真实需求来自自己的工作，能发现“看似成功其实没发出”等问题，定义验收标准，并借助 AI 把原型持续迭代成有状态、有测试、有恢复流程的工具。

## 可以放进简历的版本

**Recruiting Copilot｜招聘场景 AI 应用实践**  
技术：JavaScript / Chrome Extension MV3 / Python / IndexedDB / 本地 HTTP / SHA-256 / Node Test / unittest

- 基于实际招聘流程设计“简历读取—证据审核—单人授权—页面执行—回执核验”闭环，由外部 AI 助手输出引用原文的审核结果，执行器校验材料版本、候选人及岗位绑定。
- 在 AI 辅助下迭代 Chrome 扩展与 Python 本地服务，采用一次性许可、任务租约、持久化结果和跨进程台账锁，处理断线续接、重复回传及发送结果未知等异常。
- 针对弹窗阻塞、页面超时后延迟执行及跨批换词计数错误，补充正常控件恢复、端到端截止时间和事件驱动计数，并建立故障注入回归与隔离浏览器验证。
- 制作完全脱敏的离线交互演示，分层保存简历快照与控制状态，区分离线测试、浏览器集成验证和真实平台验收。

这版刻意不填效率提升百分比、筛选准确率、平台成功率或节约 Token 数，因为目前没有可信的前后对照数据。最终测试数量见验收报告，可以补写“通过 X 项自动化检查”，但不能写成“线上成功率 100%”。

技术职责要按自己实际能解释和完成的部分使用。如果实现主要由 AI 完成，面试时可以直接说明：“我负责业务流程、问题复现、验收与迭代，用 AI 协作完成代码和测试，并逐步理解关键模块。”不需要把 AI 协作说成独自手写全部代码。

## 90 秒讲法

“我做招聘时，反复遇到一个问题：候选人信息需要认真判断，但浏览器上的搜索、打开详情、选岗位和打招呼又很重复。我最初尝试让助手连续操作，结果遇到连接失败、弹窗挡住下一步，还有超时之后不知道到底发没发出去。

后来我把系统拆成两层。AI 负责阅读简历，给出带原文引用的判断；执行层负责检查引用、简历版本、候选人和岗位，只处理已经审核的人。

最关键的是发送可靠性。我没有把按钮点击成功当成联系成功，而是设计了 pending、verified、uncertain 状态。每次发送要有单人许可；如果已经提交但回执丢了，就先停下来核验，不能简单重试。为了恢复批次，我又把当天总量、当前批次和当前关键词的计数分开。

这一轮我还修复了快照重复写入、超时任务延迟点击和发送后弹窗的问题，补了自动化测试与独立浏览器验证，并做了脱敏演示。项目目前依赖外部 AI 助手，真实平台的长时间稳定性还需要持续验证。”

## 面试官可能追问

**这算 Agent 还是自动化脚本？**  
页面执行器是确定性工具。完整工作流由外部 AI 根据岗位、简历证据和当前状态决定下一步，再调用这些工具。不能把扩展本身说成内置大模型的独立 Agent。我的重点是把推理和有副作用的执行之间的接口做可靠。

**为什么不用一个 Prompt 直接筛人？**  
Prompt 不能替代身份和权限校验。模型可能误读，也不能控制页面晚到的响应。我让模型输出结构化证据，再用代码检查可追溯性和执行条件，unknown 保留待核实。

**幂等是什么意思？**  
同一条任务的结果重复回传，系统不会多记一次，也不会再次发消息。但“整个平台只投递一次”不是本工具能保证的。未知结果先核验，不能重跑。

**为什么 timeout 不能直接 retry？**  
超时代表我没及时拿到答案，不代表网站没执行。还有一种情况是旧页面任务仍在执行。必须区分提交前失败、提交后未知，并给页面动作传入原始截止时间。

**怎么证明修好了？**  
先复现问题，再写对应失败场景。分别验证规则单测、本机HTTP、内容脚本夹具、真实浏览器存储及MV3连接。每层只证明自己的范围，平台连续运行另做验收。

**为什么 IndexedDB？**  
简历全文体积大，不适合每次 state 都读取、复制和重写。把大文本移到按候选人读取的数据库，控制状态只保留必要信息。迁移必须等事务提交成功后才清旧字段。

**项目最大的不足？**  
模型接口尚未产品化，没有正式语义评测集；站点DOM改变仍要适配；刷新后缺少绑定的未知发送不能自动归因。长期成功率和效率收益还没有完整埋点。

**你本人具体做了什么？**  
按真实经历回答：需求来自哪些招聘动作、怎样发现误发送风险、如何定义“发出”证据、哪一次复现推动了修改、你亲自阅读和理解了哪些模块。能现场说明一条状态变化，比堆技术名词更有说服力。

## 五分钟展示路线

1. 打开 demo/index.html，先说明全部是模拟数据。
2. 选一位候选人，展开证据；指出缺证据的人不能进入发送流程。
3. 运行一次预置审核、准备和模拟发送，展示同人回执与去重。
4. 切换“回执丢失”，说明为什么进入待核验，而不立即重发。
5. 展示架构图、一次性许可和回归报告。指出 demo 模型与生产执行器的边界。

## 你先要掌握的一步

先只讲明白这句：**“没拿到回执，不等于没发出去。”**

打开离线演示，把“正常发送”和“回执丢失”各跑一次，用自己的话回答：为什么第二种情况不能直接再按一次发送？能讲清楚以后，再学任务桥、许可和数据库。不要先背所有技术名词。
